# STORM Analysis: Applying AXI, Firstmate, and no-mistakes to this skills repository

## Assumptions and scope

This analysis covers the portable skills repository in this checkout and the current public contents of [`gh-axi`](https://github.com/kunchenguid/gh-axi), [`firstmate`](https://github.com/kunchenguid/firstmate), [`axi`](https://github.com/kunchenguid/axi), and [`no-mistakes`](https://github.com/kunchenguid/no-mistakes). A follow-up compares Python review practices in [`wdm0006/python-skills`](https://github.com/wdm0006/python-skills), [`wispbit-ai/skills`](https://github.com/wispbit-ai/skills), and the supplied MCP Market listing. The goal is to improve the repo's skill authoring and agent workflows, not to turn this skills catalog into a coding-agent runtime.

The checkout tracks 52 `SKILL.md` packages under `skills/`; 11 are ToolUniverse-oriented and 3 are listed as optional. The README already separates default, optional, and science installs.

## Perspectives and interview questions

| Perspective | Question | Finding |
| --- | --- | --- |
| Skill user | How quickly can an agent choose the right workflow and act without repeated lookups? | The portable design guide already calls for focused triggers and progressive disclosure. It did not explicitly cover low-noise outputs, definitive empty states, or avoiding retrying a successful write after a failed readback. |
| Skill maintainer | How can guidance stay brief and avoid drifting from fast-changing tools? | `gh-axi` uses a small discovery skill that points to the CLI's current dashboard and help rather than maintaining a second command manual. This is a useful pattern for tool-backed skills, but a runtime dependency should remain optional. |
| Work coordinator | How should research, implementation, and review be assigned? | Firstmate separates read-only "scout" reports from authorized "ship" changes, gives parallel editors isolated worktrees, and keeps one liaison responsible for reconciling the crew's work. Its supervisor contract also uses task-specific briefs, treats overlap as a risk rather than an automatic blocker, serializes true dependencies or shared state, and avoids duplicate review gates. These refine the repo's existing independence, worktree, evaluator, and concurrency guidance. |
| Delivery gate | Where should validation happen, and what should a green result mean? | `no-mistakes` defines one opt-in, isolated path with ordered review, test, docs, lint, publish, PR, and CI steps. It distinguishes low-risk mechanical fixes from findings that require user judgment and keeps merge authorization separate from validation. This fits as an optional path in the existing workflow and publishing skill, not as a second default pipeline. |
| Portability and safety | Which upstream features fit a cross-harness skill catalog? | Compact guidance, explicit task boundaries, actionable errors, and opt-in setup transfer well. Persistent agent fleets, runtime hooks, remote secondmates, and social relays belong to an execution distro, not this portable skills catalog. |

## Synthesis and changes

The best fit is to adapt the interface principles into skill-writing and auditing guidance, not copy all ten CLI requirements into every skill. Existing skills often describe a human-facing workflow rather than a command-line product, so output schemas, exit codes, and session hooks only apply when the skill actually fronts a tool.

Applied in this checkout:

1. Added interaction-efficiency guidance to [`docs/portable-skill-design.md`](portable-skill-design.md): compact defaults, clear empty versus failed results, bounded output, actionable errors, safe retry behavior, relevant next actions, and lightweight task-based measurement.
2. Extended [`skills/skill-doctor/SKILL.md`](../skills/skill-doctor/SKILL.md) to examine avoidable calls, output noise, task routing, and tool failure states alongside context cost and overlap.
3. Added scout, ship, and evaluator task shapes and a compact brief/handoff contract to [`skills/agentic-software-workflow/SKILL.md`](../skills/agentic-software-workflow/SKILL.md). The coordinator remains the user's contact; briefs preserve scope; isolated parallel work may continue through manageable file overlap; real dependencies, shared state, and unsafe integrations serialize; routine status and duplicate review are minimized.
4. Updated [`skills/github/SKILL.md`](../skills/github/SKILL.md) to use `gh-axi` when already installed for shell-based tasks, while preserving the connected integration and raw `gh` fallbacks. The guidance also protects against ambiguous empty results and duplicate writes after failed readback.
5. Added an optional gated-delivery path to [`skills/agentic-software-workflow/SKILL.md`](../skills/agentic-software-workflow/SKILL.md) and [`skills/yeet/SKILL.md`](../skills/yeet/SKILL.md). They preserve user intent for review, avoid duplicate checks, defer intent-sensitive findings, distinguish PR readiness from merge, and leave installation opt-in. The workflow also calls for behavioral checks against an independent oracle instead of treating source-string matches as proof.
6. Kept Python review in the existing [`code-review` skill](../skills/code-review/SKILL.md), made its description explicitly match Python review requests, routed GitHub PR code reviews to it, and added a manual eval for a Python-specific mutable-default regression.
7. Verified Wispbit's Python skill and all eight rule files through GitHub. Added focused checks for required dictionary keys and operator fallback; covered side-effect and overly complex comprehensions with a concrete-clarity threshold; kept blanket import/style rules conditional.
8. Added [`python-library-review`](../skills/python-library-review/SKILL.md) for whole-package health and release-readiness audits. It adapts the `wdm0006/python-skills` library-review dimensions while keeping `code-review` focused on snippets and changes.

### AXI principle disposition

| Principle | Local disposition |
| --- | --- |
| Token-efficient output | Keep skill text, briefs, and routine tool results compact; retain evidence needed to act. |
| Minimal default schemas | Use the smallest sufficient brief and handoff; tool-backed skills should request only fields needed for the next decision. |
| Content truncation | Bound large output and explain how to retrieve the remainder when the host supports it. |
| Pre-computed aggregates | Include counts and status summaries when they avoid a follow-up lookup. |
| Definitive empty states | Distinguish a successful zero-result read from a failed or unknown read. |
| Structured errors and exit codes | Use actionable errors and safe retry guidance; preserve each host's own machine-readable contract instead of inventing a shared CLI protocol. |
| Ambient context | Keep hooks and setup opt-in and host-specific; do not add a session-time dependency to the portable catalog. |
| Content first | Prefer a useful live view for a CLI when appropriate; this is not a requirement for a static skill's no-argument behavior. |
| Contextual disclosure | Offer next steps only when they help finish or unblock the current task. |
| Consistent help | For changing CLIs, consult current command help or authoritative docs rather than maintaining a copied flag reference. |

## Defer

- Do not add a new general AXI skill: that would repeat the portable design guide and the existing skill authoring and audit paths.
- Do not install `gh-axi` or its session hooks by default. They add Node.js, authentication, and host setup requirements; use them only when already available or requested.
- Do not run `no-mistakes init` by default. It adds a named Git remote, local hooks, a background daemon, and an agent skill; repository initialization must be an explicit user choice. Avoid copying its full command guide because the upstream agent skill and CLI help are the current source of truth.
- Do not import Firstmate's entire distro, worker fleet, persistent supervision, or Relay into this catalog. Its task-boundary and worktree patterns are the reusable parts.
- Do not remove or merge skills based only on overlap in vocabulary. The repo's `skill-doctor` guidance requires evidence of redundant behavior and cautions against treating size or a lack of usage data as a deletion rule.

## Python code review sources and fit

The existing [`code-review` skill](../skills/code-review/SKILL.md) covers changed Python behavior, including mutable defaults, exceptions, resources, async boundaries, paths, and supported-version compatibility. The [`wdm0006/python-skills` library-review skill](https://github.com/wdm0006/python-skills/tree/main/skills/python/library-review) was inspected with its checklist and report template. It covers whole-library structure, distribution, API, tests, security, docs, and CI/CD, which is a distinct task from reviewing a diff.

The Wdm checklist contains useful breadth, but some thresholds and conventions are opinionated: it recommends `src/` layout, `py.typed`, `__all__`, a fixed 85% coverage bar, exact dependency pin policies, and freshness cutoffs. These should be findings only when required by the library's distribution model, user contract, or project configuration. Its report template uses dimension stars; the new local skill instead asks for evidence-backed findings and only reports dimensions that were assessed.

The [`wispbit-ai/skills` Python skill and its eight rule files](https://github.com/wispbit-ai/skills/tree/main/skills/python-expert-best-practices-code-review) were fetched through GitHub. Its critical rules cover required dictionary keys and the operator protocol; common-bug rules cover mutable defaults and generic exceptions; lower-priority rules cover list-comprehension side effects, import placement, comments, and redundant `else` blocks. Mutable defaults and broad/swallowed exceptions already overlap with `code-review`. Required-key handling and reflected operator dispatch were missing, so the existing Python checklist and manual evals now cover them. Check ignored side-effect and overly complex list comprehensions for clarity, but report their allocation cost only when it is material. Keep inline imports when they intentionally defer optional/heavy dependencies or avoid cycles; do not adopt a blanket top-of-file rule. Treat comment and `else` preferences as style unless the repo requires them or they cause a real defect. Wispbit labels its guide Python 3.14+; use each repository's declared support range instead of imposing that minimum.

Keep the change-review entry point explicit for Python snippets, diffs, and pull requests, and route full-package audits to `python-library-review`. Use the Wispbit rules as conditional review checks, not universal style gates. Keep broader library-health work separate so code-review output stays tied to changed behavior.

The supplied MCP Market URL for `python-code-review-5` remains inaccessible and did not resolve in targeted search, so its exact checklist and overlap remain unverified. No content from it was copied. The new and updated local guidance is based on the two GitHub repositories whose files were fetched.
